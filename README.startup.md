## ターミナルのみでNgRXの挙動を確認できるサンプルコードを蓄積するプロジェクト作成

- パス ./80_terminal に Angular の terminalで挙動確認用の プロジェクトを作成する
- 正確なバージョンと必要パッケージは、ユーザに改めて確認すること

Node.jsでAngular22（core・compiler）、NgRx22（store・signals）、RxJS、TypeScript、tsxを導入する。src/terminal/main.tsの先頭で@angular/compilerを読み込み、別ファイルの学習関数を呼び、console.logで出力する。依存注入はEnvironmentInjectorとrunInInjectionContextを使い、終了時に破棄する。各例は子プロセスで順番に実行する。yarn startはtsx watchで保存時に再実行し3200番で待機、yarn demoは一度だけ実行する設定にする。

timerなどで、console.log出力順がサンプルの並びと一致しないと学習者が混乱するので以下のように「待ってから実施する」仕組みで構築する
```ts
function runExamples(): void {
  run(learn01Test); // 完了後に learn02Test が実施される
  run(learn02Test);
}
```

## 目的
プロジェクト参画者が最短で理解できる資料を段階的に作成する

作成場所: x-start-docs
ファイル名: {2桁連番}_適切なファイル名.{拡張子}

## 方針
資料を作ること自体を目的にしない。
新規参画者の理解に寄与しない詳細資料は作成しない。

## 疑問
- 対応要件のブラウザは?
- テスト設計、E2Eテストは必須か?
- ドキュメントで表現されていない、タスク規約はあるか? 

## 基本規約

* 指定がない場合は Markdown で作成する。
* 内容に応じて HTML、Mermaid、シーケンス図、CSV 等を使用してよい。
* 初学者が誤った理解をしないことを最優先する。
* 確認できていない内容を事実として記載しない。
* 判断できない内容は「不明」とする。
* 合理的に推測できても確定できない内容は「推測」であることを明記する。
* 一般的な設計やベストプラクティスを、このプロジェクト固有の仕様として記載しない。
* ディレクトリ名、クラス名、関数名だけから責務を断定しない。
* ライブラリや機能が存在することと、実際に使用されていることを区別する。
* 現在使われている実装、過去の実装、サンプル、試験的コード、未使用コードを可能な限り区別する。
* 業務仕様と、コードから観測できる現在の挙動を混同しない。
* 設計理由をコードの形から推測して事実として記載しない。

## 資料について
- 記載する内容の前提として、冒頭に表形式の「まとめ」を記載する。冒頭であることを間違えないように注意
- ドメイン特有の専門用語を使用する場合で説明不足が懸念される場合、「****とは」の解説を設ける。但し「今理解する必要のある粒度」に留めること。
- 理解できたか確認するテストは不要

## 作成において
- ファイルは1ファイルずつ完成してから次に進む。但し過去に作成したファイルに誤りがある場合の修正は即時対応すること
- 読む人が記憶できないレベルで最初からあれこれ書かない。
  但し、省略した部分はその旨記載して別途既存資料の参照が必要なことを注記する。
